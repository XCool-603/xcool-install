## 第一部分：现状的打包逻辑

### 1.1 一句话

**它不是"生成一个安装包"，而是"把一个预先编译好的安装器 exe 复制过去，再在旁边放一个数据文件"。**

```
安装包 = 模板 exe（改个名） + 数据文件 install.resources + 2 个运行时 DLL
```

模板 exe 在**打包时一个字节都不改**。所有"配置"都在旁边那个数据文件里。

### 1.2 三个角色

| 角色 | 来源 | 打包时的命运 |
|---|---|---|
| `Installation.exe`（5,893,120 B） | 编译期产物，经 `Properties\Resources.resx` 以 `byte[]` 内嵌进制作工具 | 被 `File.WriteAllBytes` 原样写成 `<输出>\<用户起的名字>` |
| `DSkin.dll`（5,339,844 B） | 同上 | 原样写出 |
| `CSharpZip.dll`（225,280 B） | 同上 | 原样写出 |
| `install.resources` | **打包时现场生成** | 唯一"真的被制作出来"的东西 |

> 所以制作工具自己的 exe 有 12 MB——它把安装端模板 + DSkin 整包背在身上（`Properties\Resources.resx:259-267`）。

### 1.3 容易看晕的地方：有 3 个不同的 `*.resources` 文件

| 文件 | 位置 | 作用 |
|---|---|---|
| `SteupProject\steup.resources` | **制作工具目录** | **工作草稿**。工具启动时读它（`FrmMain.cs:40`）、新建工程时重置它（`:247`）、打包时读它（`:324`）。相当于"当前工程" |
| `<输出目录>\install.resources` | **输出目录** | **最终交付的数据文件**。由上一行复制改名而来（`:308`） |
| `<工具目录>\install.resources` | 制作工具目录 | 保存 `.dpro` 时的**中转站**（`:690`），随后被复制成 `<用户选的名字>.dpro`（`:724`） |

命名还很乱：`Steup`（少一个 t，应为 `Setup`）、`steup.resources` 与 `install.resources` 两个名字。

### 1.4 打包 9 步（`FrmMain.ThreadBuild()`，`:286-315`）

```
用户点「开始制作」
  └─ BtnStartClick (:223)
       ├─ 进度条 Maximum = 9
       ├─ IsProductInfoFull() 校验 (:618)  ← 只查 3 件事：
       │     ① 选了 exe ② exe 名必须是 a.EXE 形式 ③ 输出路径/名称非空
       │     （不校验路径合法性、不校验输出目录可写、不校验磁盘空间）
       └─ new Thread(() => ThreadPool.QueueUserWorkItem(...)).Start()   ← 线程套线程
            └─ ThreadBuild()
```

| 步 | 动作 | 行 | 细节 |
|---|---|---|---|
| 0 | `Directory.CreateDirectory(输出路径)` | `:288-291` | |
| 1 | **压缩**：`ZipHelper.ZipFileDirectory(源目录, 输出\bin.zip)` | `:293` | 递归遍历，条目名 = 相对路径（反斜杠拼接），**空目录不生成条目 → 空目录丢失**；`entry.DateTime = DateTime.Now` → 不可重现 |
| 2 | **写资源**：`CreatreSourcesInfoThread()` | `:296` → `:320-374` | 见 1.5 |
| 3 | 删除临时 `bin.zip` | `:299` | 但第 2 步已经把它的字节读进内存了 |
| 4 | 写 `DSkin.dll` | `:301` | |
| 5 | 写 `CSharpZip.dll` | `:304` | |
| 6 | **写安装包本体**：`File.WriteAllBytes(输出\<名字>, Properties.Resources.Installation)` | `:307` | 就是模板 exe 的字节 |
| 7 | `File.Copy(SteupProject\steup.resources → 输出\install.resources, true)` | `:308` | 改名复制 |
| 8 | `Process.Start("explorer.exe", 输出路径)` | `:311` | 打开目录给用户看 |

### 1.5 第 2 步在做什么（`CreatreSourcesInfoThread`，`:320-374`）

```
① 删掉旧的 SteupProject\steup.resources
② new FileStream(..., FileMode.CreateNew) + new ResourceWriter(fs)
③ 写 18 个"配置键"（都是散键，无 schema）：
     InstallProductName / InstallCompanyName / InstallProductExeName
     InstallProductVersion / InstallCompanyUrl
     InstallSetupPath / InstallationPath / InstallationExePath
     CkDesktopShortcuts / CkQuickLaunchBar / CkStartUp / CkStartClient
     BackColor / BackImage / Logo
     InstallFilesCount / LicenseAgreement / RegditFiles（拼写缺 e）
④ 把 <输出>\bin.zip 整个读进 byte[]：
     FileStream stream = new FileInfo(输出\bin.zip).OpenRead();
     Byte[] buffer = new Byte[stream.Length];
     stream.Read(buffer, 0, Convert.ToInt32(stream.Length));    ← 单次 Read，返回值未校验
⑤ writer.AddResource("bin", buffer)                            ← payload 就这样塞进去
⑥ writer.Close(); stream.Close(); fs.Close()
```

**关键特征**：
- payload 是**先落盘成 `bin.zip`、再整个读回内存**的（`:363-369`）→ 峰值内存 ≈ 2 × payload（47 MB 负载 → 100 MB+）
- `writer.AddResource("bin", buffer)` 用的是 `byte[]`，所以 `ResourceWriter` 会把整个 zip 内联进资源文件 → `install.resources` 实测 **47.9 MB**
- 所有写操作**没有 `using`**，异常路径必泄漏句柄并留下半截文件

### 1.6 数据文件里到底装了什么

19 个键，其中只有 `bin` 是真正的负载，其余 18 个是"配置"：

```
install.resources  (≈47.9 MB)
├── InstallProductName      string   产品名（= exe 名去扩展名）
├── InstallCompanyName      string
├── InstallProductExeName   string
├── InstallProductVersion   string
├── InstallCompanyUrl       string
├── InstallSetupPath        string   ← 制作机上的输出路径（安装端不读）
├── InstallationPath        string   默认安装目录
├── InstallationExePath     string   ← 制作机上的源文件夹路径（安装端不读）
├── CkDesktopShortcuts      bool     ← 安装端不读（S1）
├── CkQuickLaunchBar        bool     ← 安装端不读
├── CkStartUp               bool     ← 安装端不读
├── CkStartClient           bool     ← 安装端不读
├── BackColor               Color
├── BackImage               Bitmap
├── Logo                    Bitmap
├── InstallFilesCount       int
├── LicenseAgreement        string
├── RegditFiles             string   "a.dll;b.ocx;" 形式
└── bin                     byte[]   ← 整个 bin.zip
```

**没有文件清单**——只有一个 `InstallFilesCount` 数字。这就是为什么卸载只能"把目录全删了"、更新只能"全量覆盖"。

### 1.8 还有一条更早的路线：Delphi 裸字节拼接

`CheckDotNet\frmMain.pas:116-158`（`Button2Click`「合并文件」）：

```pascal
strmSource.loadfromfile('Stuep.exe');        strmDest.copyfrom(strmSource, ...);
strmSource.loadfromfile('CSharpZip.dll');    strmDest.seek(strmDest.size, soFromBeginning);
                                             strmDest.copyfrom(strmSource, ...);
strmSource.loadfromfile('DSkin.dll');        strmDest.seek(strmDest.size, soFromBeginning);
                                             strmDest.copyfrom(strmSource, ...);
strmSource.loadfromfile('insatll.resources');strmDest.seek(strmDest.size, soFromBeginning);
                                             strmDest.copyfrom(strmSource, ...);
strmDest.SaveToFile('Build.exe');
```

**这是"单文件安装包"的原始尝试**——把 4 个文件首尾拼成一个 `Build.exe`。旁边还有个常量 `MySize=64000; {根据编译或压缩后的文件大小进行修改}`（`:44-45`，声明后从未使用）。

它**被放弃了**，后来的 C# 版本改成"4 个文件的目录"。原因可以推测：拼接后**没有任何长度/偏移/magic**，.NET 端没法可靠地定位自己的附加数据。这是个有价值的教训——**"单文件"本身不难，难的是让读取端能可靠地找到数据**。

### 1.9 这套逻辑的 5 个结构性缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 数据文件**无 schema、无版本、无类型** | 写了没人读（4 个 `Ck*`）、强转崩溃（`BackImage` 写 `byte[0]` 读 `Bitmap`）、无法演进 |
| 2 | **数据与 exe 分离** | 漏拷 `install.resources` → 静默造空壳 → "安装成功"但什么都没装（S3） |
| 3 | **没有文件清单** | 卸载只能删光目录（H5）、更新全量覆盖留旧文件（M9） |
| 4 | 打包端与安装端的键名**靠人肉同步** | 一边改了另一边不知道，编译期无任何检查 |
| 5 | 中间文件写在**用户选的输出目录** | 中途失败残留 `bin.zip`；payload 峰值内存翻倍 |

## 第二部分：重构后的打包逻辑

### 2.1 六条设计原则（与现状的根本区别）

| # | 原则 | 现状的做法 |
|---|---|---|
| P1 | **清单先行**：先扫描出「文件清单 + 每文件 sha256」，再压缩。清单是事实来源，压缩包只是字节 | 只有一个 `InstallFilesCount` 数字 |
| P2 | **单向流水线**：每个 Stage 是纯函数，输入→输出，可单测、可重跑 | 9 步揉在一个 Form 方法里，靠 UI 字段传递状态 |
| P3 | **流式直通**：payload 直接写进最终产物，不落地中间文件，内存恒定（8 MB 缓冲） | 写 `bin.zip` → 整读进 `byte[]` → 再写进 resources |
| P4 | **打包器与读取器共用同一份格式代码**，打包完立刻回读自校验 | 打包端和安装端各写一套键名，靠人对齐 |
| P5 | **stub 与打包解耦**：stub 由 CI 编译一次并版本化，打包时只是读进来追加 | 制作工具把模板 exe 背在自己身上（12 MB），甚至曾尝试用 CodeDom 在制作机上编译（`Installation\Form1.cs`，死代码） |
| P6 | **可重现**：相同输入 + 相同版本号 → 相同字节（固定 mtime、固定条目顺序、固定压缩级别） | `entry.DateTime = DateTime.Now`（`ZipHelper.cs:160`）→ 不可重现 |

### 2.2 完整流水线

```
输入：project.wmpkg.json  +  sourceDir  +  stub.exe  +（可选）icon.ico
  │
  ├─ Stage 1  Validate    校验工程 schema、必填项、路径存在性、scope 与权限一致性
  ├─ Stage 2  Collect     递归扫描 sourceDir → FileEntry[]（相对路径、长度、mtime）
  ├─ Stage 3  Hash        逐文件流式 sha256（8 MB 缓冲，不整读）
  ├─ Stage 4  Pack        按相对路径 ordinal 排序 → payload.zip
  │                       （UTF-8 条目名、Deflate、mtime 固定、含空目录条目）
  ├─ Stage 5  Manifest    FileEntry[] + 工程元数据 + 多语言 strings → manifest.json
  ├─ Stage 6  PatchIcon   在 **stub 字节**上补丁 PE 图标（必须在追加 payload 之前）
  ├─ Stage 7  Compose     追加 stub → payload → manifest → footer
  ├─ Stage 8  Sign        signtool（必须在图标补丁之后）
  └─ Stage 9  Verify      ★ 用运行时的同一个 Reader 回读产物，断言双哈希与清单一致
  │
输出：Setup.exe（原子替换，绝不留下半截文件）
```

**Stage 9 是整套逻辑里我最看重的一步。** 打包器与读取器共用 `ContainerFormat` 的 `Write`/`Read`，所以"打出来的包装不了"这类问题**在打包阶段就暴露**，而不是等发到用户手上。现状恰好相反——打包端写什么键、安装端读什么键，两边各写一遍，只能靠人眼比对。

### 2.3 容器写入算法（伪代码）

```csharp
async Task<PackageBuildResult> BuildAsync(PackageBuildOptions o,
                                          IProgress<BuildProgress> progress,
                                          CancellationToken ct)
{
    // ── Stage 1-3：校验 + 收集 + 哈希
    Validate(o);                                             // 工程/路径/必填项
    var files = CollectFiles(o.SourceDir);                   // 相对路径 + 长度 + mtime
    await HashFilesAsync(files, ct);                         // 流式 sha256

    // ── Stage 4-5：清单先成形（payload 偏移稍后回填到 footer，不影响清单）
    var manifest = BuildManifest(o, files);                  // 含 files[] / strings / shortcuts

    // ── Stage 6：组装（写临时文件，最后原子替换）
    await using var tmp = File.Create(o.OutputPath + ".tmp");

    // ① stub —— 原样拷贝
    await using (var stub = File.OpenRead(o.StubPath))
        await stub.CopyToAsync(tmp, 1 << 20, ct);

    // ② payload —— 流式压缩，同时记账哈希（不需要二次回读）
    long payloadOffset = tmp.Position;
    var region = new Sha256RegionStream(tmp, payloadOffset);   // 转发 + 增量哈希
    await using (var zip = new ZipArchive(region, ZipArchiveMode.Create, leaveOpen: true))
        foreach (var f in files.OrderBy(x => x.RelPath, StringComparer.Ordinal))
            await AddEntryAsync(zip, f, ct);                   // UTF-8 条目名，8 MB 缓冲拷贝
    long payloadLength = tmp.Position - payloadOffset;

    // ③ manifest —— UTF-8 JSON
    long manifestOffset = tmp.Position;
    var manifestBytes = JsonSerializer.SerializeToUtf8Bytes(manifest, JsonOpts);
    await tmp.WriteAsync(manifestBytes, ct);

    // ④ footer —— 64 B，顺序写，不需要 Seek 回填
    WriteFooter(tmp, new ContainerFooter {
        Magic          = "WMINS2\0\0",
        FormatVersion  = 2,
        PayloadOffset  = payloadOffset,
        PayloadLength  = payloadLength,
        ManifestOffset = manifestOffset,
        ManifestLength = manifestBytes.Length,
        PayloadSha256  = region.Hash,        // 写入过程中算好的
        Location       = PayloadLocation.Embedded,   // 或 External（差分更新用）
        Crc32          = /* footer 自身的校验 */
    });
    await tmp.FlushAsync(ct);

    // ── Stage 7-8：图标补丁 → 签名（顺序不能反！）
    if (o.IconPath != null) PeIconPatcher.Replace(tmp.Name, o.IconPath);
    if (o.Sign)             SignTool.Sign(tmp.Name, o.SigningOptions);

    // ── Stage 9：自校验（用运行时的同一个 Reader）
    using (var verify = File.OpenRead(tmp.Name))
    {
        var info = ContainerFormat.Read(verify);                       // 只读末尾 64 B
        if (!info.VerifyPayloadHash(verify))
            throw new PackageBuildException("自校验失败：payload 哈希不匹配");
        var back = ContainerFormat.ReadManifest<InstallerManifest>(verify);
        if (back.Files.Count != files.Count)
            throw new PackageBuildException("自校验失败：清单条目不匹配");
    }

    // ── 原子替换
    File.Move(tmp.Name, o.OutputPath, overwrite: true);
    return new PackageBuildResult { /* 路径、大小、哈希、清单摘要 */ };
}
```

**几个刻意的选择**：

| 选择 | 为什么 |
|---|---|
| **footer 而不是 header** | PE 加载器忽略尾部数据，所以制作端只需"追加"，**不需要重写 PE 头、不需要 `UpdateResource`**。现状的 Delphi 方案就是栽在"没有可靠的定位信息"上 |
| **顺序写，无 Seek 回填** | 所有偏移都在写入时自然得到，一次落盘。footer 天然在最后 |
| **`Sha256RegionStream` 边写边算哈希** | 避免为了算 payload 哈希再回读一遍 47 MB |
| **写 `.tmp` 再 `File.Move`** | 打包失败绝不留下半截 exe 让用户误用 |
| **图标在签名之前** | 反过来会让 Authenticode 签名失效 |
| **zip 用 `System.IO.Compression.ZipArchive`** | 条目名**始终 UTF-8**，彻底消掉现状 `ZipConstants.cs:434` 那个"按区域 ANSI 代码页"的跨语言乱码问题；顺带不再需要内嵌的 `CSharpZipLib` |

### 2.4 读取端（stub）

```csharp
// Installer.Runtime\Program.cs
var self = File.OpenRead(Environment.ProcessPath!);
```

**注意**：stub 直接从**自身文件**流式解压到目标目录，**不需要先解压到 `%TEMP%` 再执行**——stub 自己就是安装向导。这既省一次磁盘写入，也显著降低杀软误报。

### 2.5 接口

```csharp
public interface IPackageBuilder
{
    Task<PackageBuildResult> BuildAsync(PackageBuildOptions options,
                                        IProgress<BuildProgress> progress,
                                        CancellationToken ct);
}

public static class ContainerFormat
{
    public static Task WriteAsync(Stream output, Stream stub, IEnumerable<FileEntry> files,
                                  string manifestJson, ContainerOptions opt, CancellationToken ct);
    public static ContainerInfo? Read(Stream input);                       // 只读 footer
    public static T ReadManifest<T>(Stream input);
    public static Stream OpenPayload(Stream input);                        // 已定位的子流
}
```

**打包器不认识"安装"**。打包器只产出文件，安装器只消费文件，两者唯一的共享契约是 `Installer.Abstractions` 里的 `InstallerManifest` DTO + `ContainerFormat`。所以：

- GUI 和 CLI 调的是**同一个** `BuildAsync`
- 安装端和卸载端调的是**同一个** `ContainerFormat.Read`
- 清单的 schema 只有一个定义处，编译期就能发现不匹配

### 2.6 命令行（现状完全没有的能力）

```bash
installer-cli pack    --project app.wmpkg.json --source .\publish --out .\dist\Setup.exe \
                      --icon app.ico --sign
installer-cli inspect .\dist\Setup.exe          # 打印 manifest + 校验 payload 哈希
installer-cli extract .\dist\Setup.exe -o .\out # 反解出 payload 与 manifest
installer-cli diff    v2.4.0\Setup.exe v2.4.1\Setup.exe   # 两个包的清单差异
```

`inspect` / `extract` / `diff` 三个命令现状**一个都做不到**（数据在二进制 resources 里，没有工具能看）。它们带来的能力：

- `inspect` → 排查"这个包装的是什么、对不对"不用装一遍
- `extract` → **支持"导入已有安装包 → 修改 → 重新打包"**（现状不支持）
- `diff` → 为差分更新打基础（知道哪些文件变了）

```
<产品名>_Setup_<版本>.exe        例：AutoTown_Setup_2.4.1.exe
```

多语言包不加语言后缀（一个包全球通用，见重构方案 §9.3）。

## 第三部分：一一对照

| 维度 | 现状 | 重构后 |
|---|---|---|
| **本质** | 复制模板 exe + 旁边放数据文件 | 组装一个自包含容器 |
| **打包器做的事** | 压缩 → 写 resources → 复制 exe/dll → 改名 | 收集 → 哈希 → 压缩 → 写清单 → 组装 → 补图标 → 签名 → 自校验 |
| **数据载体** | `.NET ResourceWriter` 二进制，19 个散键 | `manifest.json`（UTF-8 + `schemaVersion` + 强类型） |
| **文件清单** | 无（只有 `InstallFilesCount` 一个数字） | `files[]` + 每文件 sha256 |
| **中间文件** | `bin.zip` 落在用户选的输出目录 | 无（流式直通） |
| **峰值内存** | ≈ 2 × payload | 恒定 8 MB 缓冲 |
| **交付物** | 4 个文件的目录 | **1 个 exe** |
| **完整性校验** | 无 | footer 里的 `payloadSha256` |
| **打包后自检** | 无 | Stage 9 用同一个 Reader 回读校验 |
| **打错了何时发现** | 到用户手上 | 打包阶段就报错 |
| **可反解** | 不能 | 能（`extract`） |
| **可重现** | 不能（zip mtime = `DateTime.Now`） | 能（固定 mtime + ordinal 排序 + 固定压缩级别） |
| **空目录** | 丢失（`ZipSetp` 不为目录生成条目） | 保留 |
| **条目名编码** | 区域 ANSI 代码页（`ZipConstants.cs:434`） | 恒定 UTF-8 |
| **打包入口** | 只能点 GUI | GUI + CLI（可进 CI） |
| **制作机需要什么** | 需要 VS + 能跑 DSkin（曾试图用 CodeDom 现场编译） | 只需一个自包含的 `Installer.Builder.exe`/`Cli.exe` |
| **语言** | 写死中文 | 打包期固化成多语言 `strings` 表 |
| **打包与安装的耦合** | 靠人肉对齐键名 | 共享 `ContainerFormat` + `InstallerManifest` DTO |

---

## 第四部分：为什么我认为这套逻辑更对

1. **它把"配置"从"二进制黑箱"变成了"可读的清单"。** 现状最大的问题不是"用了二进制"，而是**没有任何契约**——写端和读端各写一遍键名，编译器帮不上忙。清单 + 共享 DTO 把这件事变成编译期错误。
2. **清单先行让"卸载/更新/修复/差分"四个能力同时成立。** 现状一个都没有，全是因为没有文件清单。
3. **单文件是自然结果，不是额外工作。** 容器格式本来就是一个文件；额外工作只有 stub 自包含与 PE 图标补丁两件。
4. **自校验把"打包错误"从用户侧挪到了构建侧。** 这是投入最小、收益最大的一步。
5. **打包器与 UI 解耦后，打包可以进 CI。** 现状"打包必须点 GUI"，意味着每次发版都是手工操作，无法审计、无法重现。

> 唯一要提醒的取舍：**单 exe 无法做差分更新**。所以我保留了 `PayloadLocation.External` 这个口子——同一容器格式，payload 可以内嵌（单 exe，默认）或外置（`setup.exe` + `payload.pkg`，给增量更新用）。将来要加在线更新时，不需要改格式。
