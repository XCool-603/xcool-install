## 3. 快速上手

### 3.1 构建

```powershell
# 需要 .NET SDK（本机 9.0.305）+ .NET Framework 4.8 目标包
dotnet build Installer.sln -c Debug
```

### 3.2 测试

```powershell
# 单元测试（90 项）
dotnet test tests\Installer.Core.Tests\Installer.Core.Tests.csproj

# 端到端验收（52 项断言：打包 → 隔离安装 → 逐字节比对 → 篡改检测 → Zip Slip）
powershell -ExecutionPolicy Bypass -File tools\e2e.ps1
```

> ⚠️ `tools/e2e.ps1` **必须以 UTF-8 with BOM 保存**。Windows PowerShell 5.1 会把无 BOM 的 `.ps1` 按 ANSI 读，中文注释会导致语法错误。

### 3.3 打包一个安装包

**① 写工程文件 `app.wmpkg.json`**（内容就是 `InstallerManifest`，`files` 由打包器填充）：

```json
{
  "schemaVersion": 2,
  "productCode": "{8F3A1C2E-5B4D-4E7A-9C1F-2D3E4F5A6B7C}",
  "defaultCulture": "zh-Hans",
  "cultures": ["zh-Hans", "en"],
  "product": {
    "name": { "zh-Hans": "汽车小镇", "en": "Auto Town" },
    "version": "2.4.1",
    "publisher": { "zh-Hans": "唯非工作室", "en": "WeiFei Studio" },
    "url": "https://example.com"
  },
  "scope": "perUser",
  "defaultInstallDir": "%LOCALAPPDATA%\\Programs\\AutoTown",
  "entryPoint": "bin\\AutoTown.exe",
  "shortcuts": [
    { "location": "Desktop", "name": { "zh-Hans": "汽车小镇", "en": "Auto Town" } }
  ],
  "strings": {
    "Button.Install": { "zh-Hans": "立即安装", "en": "Install" }
  }
}
```

**② 打包**：

```powershell
installer-cli pack --project app.wmpkg.json --source .\publish --stub Installer.Runtime.exe `
                   --out .\dist\Setup.exe --icon app.ico --build-time 2026-10-08T12:00:00Z
```

**③ 验证与排查**：

```powershell
installer-cli verify  .\dist\Setup.exe            # 校验双哈希 + 清单 + 清单与 payload 一致性
installer-cli inspect .\dist\Setup.exe            # 打印容器索引 + manifest.json 全文
installer-cli extract .\dist\Setup.exe --out .\x  # 反解出 payload 与 manifest（可再打包）
installer-cli diff    a\Setup.exe b\Setup.exe     # 文件清单差异（为差分更新打基础）
```

**④ 运行**（当前 stub 无向导 UI，走无人值守）：

```powershell
# 安装（推荐带 --sandbox 做测试，避免污染真实系统）
.\dist\Setup.exe --silent --sandbox C:\test\sandbox --result r.json
.\dist\Setup.exe --silent --target "C:\Program Files\MyApp"     # 真实安装
.\dist\Setup.exe --silent --culture en                          # 指定界面语言
.\dist\Setup.exe --silent --dry-run                             # 只走流程不落盘
.\dist\Setup.exe --silent --verify-only                         # 只校验，不安装

# 卸载（由「程序和功能」调用；沙箱根从安装记录里读，不需要再传）
"C:\Program Files\MyApp\Uninstall.exe" --uninstall
```

退出码：`0` 成功 / `1` 失败 / `2` 用法错误。

## 4. 容器格式规格（v2）

```
setup.exe
├── [0, payloadOffset)              模板 stub（PE 结构）
├── [payloadOffset, +payloadLength) payload.zip（UTF-8 条目名）
├── [manifestOffset, +manifestLength) manifest.json（UTF-8，缩进，可 diff）
└── [fileLength-128, fileLength)    footer（128 字节，小端）
```

### footer 字段表（`ContainerFormatSpec` 是唯一定义处）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 8 | magic | `"WMINS2\0\0"` |
| 8 | 4 | formatVersion | 当前 2 |
| 12 | 4 | flags | bit0 = payload 外置（预留） |
| 16 | 8 | payloadOffset | |
| 24 | 8 | payloadLength | |
| 32 | 8 | manifestOffset | |
| 40 | 4 | manifestLength | |
| 44 | 4 | reserved | |
| 48 | 32 | payloadSha256 | |
| 80 | 32 | **stubSha256** | 只校验 payload 挡不住"改安装器代码" |
| 112 | 4 | footerCrc32 | 覆盖前 112 字节 |
| 116 | 12 | reserved | |

**为什么 footer 在末尾**：PE 加载器忽略尾部数据，所以打包端只需"追加"——不需要重写 PE 头、不需要 `UpdateResource`、不需要 Seek 回填。

## 5. 实现过程中发现并修掉的坑

这几条是**踩过才知道**的，写下来避免以后重犯。

### 5.1 `.NET ZipArchive` 不支持非 0 起始位置 ⚠️

在 `ZipArchiveMode.Create` 下，`ZipArchive` 会把**绝对流位置**写进 EOCD 的「中央目录起始偏移」。

实测：在偏移 100 处写一个 115 字节的 zip，EOCD 记录偏移 **142** → 一旦按 payload 区间单独解压就报 `Int64 无法容纳中央目录偏移量`。对照组（偏移 0）正常。

**解决**：`OffsetWriteStream` —— 让 ZipArchive 始终看到从 0 开始的逻辑位置，底层仍顺序写到容器的 payload 区间（无中间文件、内存恒定）。

### 5.2 自校验抓到了我自己打包器的 bug

`Hashing.ComputeRegionBytes` 会把流定位到 payload 区间末尾。原始代码在计算 payload 哈希**之后**直接写 footer，导致 **footer 被写在 manifest 上面**。

这正是 `BuildStage.Verify` 存在的意义：用运行时的同一个 Reader 回读，打包阶段就暴露问题，而不是等发到用户手上。

### 5.3 stub 的 PE 头部默认没有余量

`FileAlignment=512`（Roslyn 默认）时 `SizeOfHeaders == 第一个节 PointerToRawData`，头部零余量 → 图标补丁无法新增节表项。

**解决**：stub 的 csproj 里 `<FileAlignment>4096</FileAlignment>`，头部余量从 0 变成 3600 字节。

### 5.4 嵌入资源需要显式元数据

用 MSBuild 目标往 `@(EmbeddedResource)` 里动态加项时，必须同时设：

```xml
<Type>Non-Resx</Type>
<WithCulture>false</WithCulture>
```

否则 `Microsoft.Common.CurrentVersion.targets` 的 `_CoreCompileResourceInputs` 筛选会把它们**静默丢掉**（编译能过，但资源没进去，运行时报缺程序集）。

### 5.5 工程文件与安装包清单的校验强度不同

`.wmpkg.json`（工程）本来就没有 `files`（由打包器扫描填充），而安装包清单**必须**有 `files`。

**解决**：`ManifestSerializer.Validate(m, requireFiles)`；`Deserialize` 用宽松模式，`ContainerFormat.ReadManifest` 用严格模式。

### 5.6 只校验 payload 是不够的

最初的容器只存 payload 哈希。篡改测试（改偏移 3000 的字节）**通过了 verify** —— 因为那个位置在 stub 区间。

**解决**：footer 增加 `stubSha256`，verify 与安装端都校验两者。

### 5.7 端到端测试差点污染真实系统 ⚠️

第一版 e2e 的"隔离安装"那一步**忘了加 `--sandbox`**，于是它：
- 在**真实注册表**里写了一个卸载键（产品真的出现在了「程序和功能」里）
- 在**真实桌面**上创建了一个 `.lnk`

我是复查时发现的，已精确清理，并在 e2e 里加了**回归护栏**（第 13 节）：断言真实注册表 / 桌面 / 开始菜单 / Run 键里都没有本次的痕迹。
只要以后有人把 `--sandbox` 去掉，那四条断言会立刻失败。

**教训**：涉及注册表和 shell 位置的测试，必须默认沙箱，而且要有"零污染"的显式断言——不能只靠"我记得加参数"。

### 5.x 使用者反馈出来的三个问题（都已修）

这三条**不是我自己测出来的，是拿去用之后反馈的** —— 记在这里因为它们比自测发现的更有价值。

**① "安装到 D 盘，但文件还是装到 C 盘了"（严重）**

两个 bug 叠在一起：

- `WizardPresenter.ApplyToManifest()` 写了快捷方式、自启动、装完运行，**唯独漏了安装位置**
- 就算写了也没用：`WizardHostImpl` 用的是**构造时捕获的 `_installDir` 快照**，不是清单里的当前值

结果就是用户在向导里把路径改成 `D:\`，界面显示了 `D:\`，装完还在 `C:\` —— 而且**没有任何报错**。

修法：`ApplyToManifest` 补上 `DefaultInstallDir`；`WizardHostImpl` 改成每次从清单读（`EffectiveInstallDir`）。
回归测试：`用户在向导里改的安装位置必须写回清单`、`换一个盘符也要生效`；e2e 第 18 节断言"指定的安装位置必须真的生效"。

**教训**：状态快照和状态源不一致，是静默失败的高发区。凡是"用户能改、引擎要读"的值，引擎必须**每次去读**，不能在构造时抓一份。

**② "dotnet build 时好时坏"（NETSDK1047）**

SDK 对 net48 会自己推 `RuntimeIdentifier`：

| PlatformTarget | Prefer32Bit | 推出的 RID |
|---|---|---|
| AnyCPU | false（SDK 对 net48 的默认） | `win-x64` |
| x86 | — | `win-x86` |

而 `dotnet restore` 有时不生成这个 RID 目标，于是 build 报"资产文件没有 net48/win-x64 的目标"。
**同一份代码，restore 过一次就坏、清干净又好。**

修法：所有项目**显式钉死** `PlatformTarget` + `RuntimeIdentifier`，并加 `AppendRuntimeIdentifierToOutputPath=false` 把输出路径钉回 `bin\Debug\`。
分层规则：**库 = AnyCPU 无 RID，exe = x86 + win-x86，测试宿主跟 exe 同位数**（否则 64 位宿主加载 x86 程序集会 `BadImageFormatException`）。

**教训**：SDK 的隐式推导一旦和 restore 的推导路径不一致，就是"时好时坏"。凡是构建要用的关键属性，显式写出来。

**③ "内容和输出都得选，模版还得选，这个界面就不是给人用的"**

见 §9.2 —— 制作端界面整个重做了。

**教训**：第一版是照"清单里有什么字段"来排界面的，不是照"用户要做什么"来排的。字段驱动 → 标签页爆炸；任务驱动 → 一屏三步。

**④ "装了三次，控制面板里出现三次；卸载了一个，其余删不掉了"（严重）**

两个 bug 叠在一起，而且是**互相放大**的：

- **根因**：制作端每次打开都调 `BuilderDocument.CreateDefault()` → 生成**新的 productCode**。
  同一个产品打三次包，就是三个不同的卸载键 —— 控制面板里三条记录，全都指向同一个安装目录。
- **放大器**：卸载器**没有安装记录就直接报错退出**。第一条卸载把 `.install-record.json` 删了，
  剩下两条点"卸载"就永远没反应（Windows 也只会去启动那个 exe，exe 自己拒绝干活）。

修法三处：
① 制作端把上一次的工程**自动记到** `%APPDATA%\安装包制作助手\last.wmpkg.json`，下次打开接着用 → productCode 稳定；
② 安装时新增 `cleanup-orphans` 步骤：清掉"同一个安装目录、但 productCode 不同"的残留卸载键 → 重复安装只留一条；
③ 卸载器支持**降级卸载**：没有记录也能按"卸载键里写的安装目录"定位，把指向本目录的键全清掉；
   同时 `UninstallString` 里带上 `--product-code {…}`，记录丢了也能精确定位。

回归测试：`UninstallKeysTests`（10 条）+ `DegradedUninstallTests`（5 条）+ e2e 第 19 节
（两次安装只留 1 条、删掉记录后仍能降级卸载并清空卸载项）。

**教训**：一个"每次运行都变"的标识符，只要被写进系统里的持久位置，就一定会变成数据事故。
productCode 是身份，身份不能每次重新生成。

**⑤ "快捷方式都挡住了" + 布局算错（用户反馈）**

`bodyLayout` 的固定行高合计 566，而窗口只能给 548 —— **差 18px**，最后一行被裁。
卡片内高也不够（folderStep 要 240，卡片只给 236）。

改法：把窗口高度按算式定下来，并**把算式写进注释**：

```
窗口高 = 上边距 + 页头 + Σ卡片 + 高级按钮 + 输出区 + 状态栏
每个卡片高 = 子控件需要的高度 + 28（上下各 14 内边距）
```

**教训**：`TableLayoutPanel` 里用 `Absolute` 行高时，总和超过容器就是静默裁剪 ——
不会报错，只会"挡住"。加卡片时一定要重算总和。

**⑥ 加载工程会把快捷方式悄悄清空（严重，且极难发现）**

`WriteToViews()`（模型 → 视图）里设置 `infoStep` 的文本框会触发 `TextChanged`
→ 回调 `UpdateOutputPath()` → `ReadFromViews()`（视图 → 模型）
→ 用**还没同步的**快捷方式复选框（false）覆盖清单。

结果：打开一个带快捷方式的工程，快捷方式全没了 —— 而且界面上看不出任何异常。

修法：**模型 → 视图的同步必须是一次原子操作**，期间任何控件事件都不能反过来写模型。

```csharp
private void WriteToViews()
{
    var wasInitializing = _initializing;
    _initializing = true;          // 期间所有 Changed 回调直接 return
    try { WriteToViewsCore(); }
    finally { _initializing = wasInitializing; }
}
```

**教训**：双向绑定里，"写视图"和"读视图"必须有明确的单向边界。
没有边界的后果不是报错，是**静默的数据丢失**。

**⑦ 开发用的截图模式污染了用户的工程（我自己造成的）**

`--render-ui` 走的是正常的 `Close()`，而 `FormClosing` 里会 `AutoSave()` ——
于是**我每跑一次截图，就把用户记住的工程覆盖一次**（sourceDir 变成我的演示目录，
快捷方式被清空）。

修法：加 `_rendering` 标记，截图模式**既不读也不写**自动记忆，并从干净的默认工程开始渲染。

**教训**：开发/验收用的旁路入口，必须和用户的持久化路径**物理隔离**。
"顺手复用正常流程"在这里就是数据事故。

> 另外，排查 ⑥ 的过程也值得记：我先怀疑颜色、再怀疑自动记忆、又翻了 AntdUI 源码，
> 全都不对。最后**在每一步插桩打印**，一次就定位到了。
> **插桩 > 推理**，和前面"采样像素 > 目测"是同一条教训。

## 7. 安装与卸载管线（M1 / M2 已落地）

### 7.1 九个安装步骤

```
preflight → kill → extract → shortcuts → autostart → uninstall-info → deploy-uninstaller → install-record → run-after-install
```

| # | 步骤 | 关键点 | 修掉的现状问题 |
|---|---|---|---|
| 1 | `preflight` | 路径合法性（拒绝盘根/系统目录）、磁盘空间、版本比较用 `System.Version`、已装更高版本则拒绝 | 无磁盘检查；`Int32.Parse(v.Replace(".",""))` 版本误判 |
| 2 | `kill` | 按 **exe 名**匹配进程 | 现状按"产品显示名"匹配，基本无效 |
| 3 | `extract` | 全部路径过 `SafePath`；**清单里的文件必须全部落地**，否则失败 | Zip Slip；`catch{}` 导致"安装成功但文件缺失" |
| 4 | `shortcuts` | 真实 `.lnk`（IShellLink），名字按语言取 | 制作端勾选被忽略（写了没人读的键） |
| 5 | `autostart` | **与 scope 一致**：perUser→HKCU，perMachine→HKLM | 现状无条件写 HKLM，且卸载从不删 |
| 6 | `uninstall-info` | **标准**卸载键 `...\CurrentVersion\Uninstall\{ProductCode}`，10 个值齐全 | 现状写私有键 `WayMark\<产品>`，值名拼成 `UnInstallationString` 且指向不存在的文件 |
| 7 | `deploy-uninstaller` | **只拷自己文件的前 `StubLength` 字节**（stub 部分） | 若拷整个安装包，卸载器会白背几十 MB payload |
| 8 | `install-record` | 写 `.install-record.json`（文件清单 + 哈希 + 快捷方式 + 注册表值 + 沙箱根） | 现状没有清单概念 |
| 9 | `run-after-install` | 失败只警告，不让整个安装失败 | 无存在性检查 |

### 7.2 回滚：写前日志（write-ahead journal）

**唯一的硬性约定**：步骤里每做一个写操作，就必须先往 journal 记一条可逆记录。

```csharp
JournalWriter.WriteFile(ctx, Id, target, p => File.WriteAllBytes(p, data));
JournalWriter.SetRegistryValue(ctx, Id, hive, subKey, name, value, false);
JournalWriter.CreateShortcut(ctx, Id, linkPath, target, ...);
```

失败或取消时，引擎**逆序 undo journal**：

| journal 记录 | 撤销动作 |
|---|---|
| `CreateDirectory` | 是空目录就删（非空保留 —— 说明不是我们建的，或用户放了东西） |
| `WriteFile` | 之前不存在 → 删；之前存在 → 从 `.rollback\NNNNNN.bak` 还原 |
| `SetRegistryValue` | 之前不存在 → 删值；之前存在 → 还原旧值 |
| `CreateShortcut` | 删 |
| `CreateSubKey` | 递归删整棵子键 |

**为什么不让每个步骤自己实现 `Rollback`**：那样在"步骤执行到一半抛异常"时必然撤不干净。journal 方案记录的是**实际落下的每一个写操作**，所以能精确撤销。这一点有专门的单元测试覆盖（`步骤执行到一半抛异常时已落下的写入也要被撤销`）。

journal 是 jsonl，**每写一条就落盘**，所以进程被杀也能在下次启动时用 `InstallJournal.LoadPending()` 读回做诊断。

### 7.3 卸载：按记录精确删

```
UninstallEngine:
  ① 结束正在运行的程序
  ② 删快捷方式（来自安装记录）
  ③ 删开机启动项 + 删标准卸载键
  ④ 按清单删文件（内容被改过的也删，但记进 modifiedFiles）
  ⑤ 自底向上删空目录（非空的保留）
  ⑥ 复制自身到 %TEMP% → 副本删掉 Uninstall.exe/记录/日志 → 删空目录 → 自删除
```

**与现状最关键的区别**：现状（`FrmUnInstall.cs:232-257`）递归删光 `Application.StartupPath` 下的一切。
现在只删记录里列出的文件 —— e2e 里专门放了一个"用户自己的文件"并断言**卸载后它还在**。

**自删除不用 bat**：现状用 `Encoding.Default` 写 `~del.bat`（英文系统是 Windows-1252，含中文路径就乱码）。
现在用"复制到 `%TEMP%` → 副本收尾 → `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)`"，没有编码问题。

### 7.4 沙箱模式

```powershell
Setup.exe --silent --sandbox C:\test\sandbox --result r.json
```

把**快捷方式、注册表、自启动**全部重定向到指定目录（注册表落到 `sandbox\registry.json`），
不碰真实系统。用途：

- **端到端测试** —— 否则跑一次 e2e 就会在真实的「程序和功能」里留下垃圾（这一点我踩过，见下）
- 便携安装

沙箱根会写进安装记录，所以**卸载时不需要再传 `--sandbox`**，卸载器会自己还原到同一个沙箱。

### 7.5 运行参数

| 参数 | 说明 |
|---|---|
| `--target <目录>` | 安装目录 |
| `--silent` | 不弹界面 |
| `--culture <语言>` | 界面语言（`en` / `zh-Hans`），默认跟随系统 |
| `--sandbox <目录>` | 沙箱模式 |
| `--result <文件>` | 结果 JSON |
| `--dry-run` | 只走流程不落盘 |
| `--verify-only` | 只校验容器与哈希 |
| `--uninstall` | 按安装记录卸载（控制面板调用） |

退出码：`0` 成功 / `1` 失败。

## 8. 向导界面（M3 已落地）

### 8.1 页面与状态机

```
欢迎 → 许可协议 → 安装位置 → 选项 → 正在安装 → 完成
                                        └──────→ 失败（可重试）

卸载：卸载确认 → 正在卸载 → 卸载完成
```

状态是 **`WizardPage` 枚举**，文案只是它的输出：

```csharp
public enum WizardPage { Welcome, License, Path, Options, Installing, Finish, Failed, ... }

// 主按钮返回的是"文案 key"，不是已翻译的文字
public string PrimaryKey { get { switch (Current) { case WizardPage.Options: return "Wizard.Install"; ... } } }
```

**这条设计直接消灭了现状最致命的地雷**：现状用按钮文字当状态
（`FrmInstallation.cs:173` `BtnInstall.Text.Equals("立即安装")`、`FrmUnInstall.cs:117` `"狠心卸载"`），
界面一翻译成英文，安装/卸载立刻失效。现在有专门的测试钉死这一点：

- `主按钮返回的是文案_key_而不是已翻译的文字`
- `切换语言不会改变状态机行为`（同一串操作在中英两版下状态序列必须完全一致）
- `同一状态下中英两版的主按钮文案不同但_key_相同`

### 8.2 双语是默认行为

`WizardStrings.CreateDefault()` 内置了 40+ 条**中英对照**文案，清单里的 `strings` 可以逐条覆盖：

```jsonc
"strings": {

}
```

所以：**制作端什么都不做，向导默认就有英文**；`--culture en` 出来的界面是全英文的
（e2e 里断言了中英两版的渲染结果必须不同）。

覆盖是**逐语言**的 —— 清单只给 `en` 时，`zh-Hans` 仍用内置文案（有测试）。

### 8.6 AntdUI 版本坑（实测）

| 项 | 2.4.3 的真实情况 |

| `Progress.Value` | `float`，**范围 0–1**，没有 `Maximum`/`Minimum` |

| `TVariant` | 只有 `Outlined` / `Undefined` 两个值 |
| `Checkbox.CheckedChanged` | 是 `BoolEventHandler`，`e.Value` 取新状态（不是 `EventHandler`） |
| `Modal.Config` | 有 `(Form, string, string)` 构造，但**没有** `OkText`/`CancelText` 属性 |
| `Steps.Items.Add` | 参数是 `StepsItem` 对象 |
| `BaseForm` | 仍带系统标题栏（不是无边框窗口） |

## 9. 制作端 GUI（M4 已落地）

### 9.1 工程文件：可读、可 diff、可手写

现状的工程文件是**改了扩展名的二进制资源文件**（`.dpro`），只能用它自己的程序打开，
出问题没法查、进不了版本控制、也没法在 CI 里生成。

新格式是 JSON，而且**两种写法都认**：

```jsonc
// ① 裸清单（手写最省事）
{ "schemaVersion": 2, "productCode": "{...}", "product": { ... }, "scope": "perUser" }

// ② 完整工程（制作端存出来的）
{ "manifest": { ... }, "build": { "sourceDir": "...", "stubPath": "...", "outputPath": "..." } }
```

`ProjectSerializer` 自动识别。命令行参数优先于 `build` 段，所以 CI 可以覆盖：

```powershell
installer-cli pack --project app.wmpkg.json                    # 全部走工程文件
installer-cli pack --project app.wmpkg.json --out D:\ci\S.exe  # 只覆盖输出路径
```

> 坑：`JObject.Parse` 会把 `"2026-10-08T12:00:00Z"` 认成 **DateTime**，转回字符串就变成
> `"10/08/2026 12:00:00"`，可重现构建直接失效。必须用 `JsonTextReader` 配
> `DateParseHandling.None` 来解析。有测试钉住。

### 9.2 界面：一屏三步（第一版做砸了，已重做）

**第一版是 5 个标签页，被使用者直接骂了**："内容和输出都得选，模版还得选，这个界面就不是给人用的。"
骂得对。复盘一下错在哪：

| 第一版（错） | 问题 |
|---|---|
| 让用户选**模板 stub** | 那是工具自己的零件，凭什么让用户去文件系统里找 |
| 让用户选**输出路径** | 能自动推出来，没必要问 |
| **5 个标签页** | 真正必填的只有 3 项，其余都是噪音 |
| **构建时间戳**摆在主界面 | 那是 CI 的事，不是每个制作的人都要管的事 |
| 产品标识 / 安装范围 / 安装目录 / 主题色 / 网址 | 全是"设一次就不再动"的东西，却占了 3 个页面 |

**重做后的主界面就是三步：**

```
安装包制作助手                                            [中文 ▾]

第 1 步 · 选择要打包的文件夹
```

## 10. COM 注册与修复安装（M5 已落地）

### 10.1 现状的做法是错的

`FrmInstallation.cs:486-492`：

```csharp
// 先复制到 System32
File.Copy(dll, Path.Combine(Environment.SystemDirectory, name), true);
// 再 regsvr32，参数不加引号
p.StartInfo.Arguments = "Regsvr32.exe /s " + fullPath;
p.StartInfo.UseShellExecute = false;
p.StartInfo.Verb = "runas";        // ← 被忽略
// 异常被空 catch 吞掉
MessageBox.Show("注册成功");        // ← 无论成没成都说成功
```

四个问题：
1. **复制到 `System32`** —— 污染系统目录、需要管理员、而且程序自己反而找不到组件
2. **参数不加引号** —— 代码注释自己写着"路径中不能有空格"
3. **`Verb="runas"` 与 `UseShellExecute=false` 冲突** —— 后者让前者失效
4. **异常被吞** —— 失败也报成功

### 10.2 新实现

```csharp
public static ComRegistrationResult Apply(string dllPath, string mode, bool register)
```

| 方式 | 说明 |
|---|---|
| `regsvr32`（**默认**） | 调用 regsvr32，**不复制到 System32**，路径加引号，`BeginOutputReadLine` + `BeginErrorReadLine` 两个流都读（避免管道写满死锁），退出码非 0 报错并翻译含义 |
| `direct` | 本进程内 `LoadLibrary` + `DllRegisterServer`。适合 regsvr32 被安全软件拦截的环境；代价是坏 DLL 会拖垮安装器进程 |
| `registrationFree` | **明确报错说"尚未实现"**，并告诉用户该改成哪个值 —— 不假装成功 |

regsvr32 退出码有可读解释（有测试）：

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 3 | 找不到 `DllRegisterServer` / `DllUnregisterServer` 导出 |
| 4 | `LoadLibrary` 失败（不是有效 DLL，或**位数不匹配**） |
| 5 | `DllInstall` 失败 |

### 10.3 回滚怎么处理

DLL 自己往注册表里写的内容**无法逐条记录**，所以 journal 里记的是
"注册过这个文件"（`JournalOps.RegisterCom`），撤销方式是**反过来调用 `DllUnregisterServer`**。

记录顺序是**先记再注册** —— 这样即使 `DllRegisterServer` 写了一半才失败，回滚也会去反注册。

### 10.4 卸载顺序

```
… → 清理注册表 → **反注册 COM** → 删除文件 → …
```

**必须在删文件之前反注册** —— DLL 被删掉之后就再也反注册不了了，注册表里会留下死项。
安装记录里存了 `com[]`（绝对路径 + 方式），所以卸载不依赖原安装包。

### 10.5 修复安装（`--repair`）

```powershell
Setup.exe --repair --target "C:\Program Files\MyApp"
```

修复模式下 `ExtractPayloadStep` 会：

1. 从清单里取出每个文件的 `sha256`
2. 文件存在且哈希一致 → **直接跳过，不碰它**
3. 缺失或哈希不一致 → 重新写入，并记日志

所以修复是**幂等**的，而且不会无谓地重写几万个没坏的文件（e2e 里断言了幂等）。


### 11.2 顺手印证了一条分析结论

`legacy-inspect` 会把原始键全列出来，真实包里赫然有：

```

InstallationExePath = D:\Worker\长隆项目\古海幻行(6座悬挂AR)\工程文件\执行文件\CSVS执行程序
```

**制作机路径确实被打进了发布包**（`FrmMain.cs:489-490` 那一带的逻辑）。
新格式里 `Collect` 阶段只记录**相对路径**，有测试断言反解出的 manifest 不含制作机路径。

### 11.3 迁移成新工程

```powershell
installer-cli legacy-import Installation\bin\Debug --out app.wmpkg.json
```

产出可读的 `.wmpkg.json`，产品名/版本/厂商/入口程序/许可正文/COM 文件都被翻译过去，
`RegditFiles` 变成 `com[]` 且方式为 `regsvr32`（v1 只会 regsvr32，不能假装是免注册）。

两条诚实的提示：

- **`productCode` 是新生成的** —— v1 里根本没有这个概念，命令会明确说出来
- **制作机路径不会被带过去** —— 有测试断言

### 11.4 一个已知的历史包袱

v1 的 zip 条目名是按**当时的区域 ANSI 代码页**编码的
（`CsharpZipLib\Zip\ZipConstants.cs:434`，`defaultCodePage = CultureInfo.CurrentCulture.TextInfo.ANSICodePage`）。
在中文机器上打的包，换到英文机器解压就是乱码。

所以迁移只还原**元数据**；文件清单要靠重新打包时扫描源目录。
这份真实包的条目名恰好都是 ASCII，所以能正常读出来。

## 13. 已知限制

1. **向导没有"安装前/后脚本"、语言切换按钮、自定义页面** —— 目前是固定的六页流程。
2. **免注册 COM 未实现** —— 需要从类型库导出 CLSID 并写 `<App>.exe.manifest`；当前会明确报错，不假装成功。
3. **修复安装只按哈希补齐，不做"修复注册表/快捷方式"** —— 那两类由安装步骤本身保证幂等。
4. **v1 包只能读元数据，不能还原文件清单** —— 见 §11.4 的代码页问题。
5. **外置 payload（差分更新）未实现** —— 容器 flags 位已预留，`PackageBuilder` 会明确抛 `NotSupportedException`。
6. **图标补丁会使 Authenticode 签名失效** —— 所以顺序必须是"补图标 → 签名"。签名代码已实现（`SignToolRunner`），按用户要求**不做签名验证**。
7. **PE 补丁器限制**：无资源目录的 PE、资源树深度 >3 层、语言层用字符串名 → 抛 `NotSupportedException`。
8. **`verify` 不是签名的替代品** —— 哈希存在同一个文件里，只能防意外损坏与低级篡改；防恶意替换必须靠 Authenticode 签名。
9. **未实现标准静默安装参数**（`/S`、`/D=`）—— 当前用的是自定义的 `--target/--silent/--result/--repair`。
10. **`EstimatedSize` 按 KB 取整**，小包会算成 0。
11. **卸载器在 `%TEMP%` 留一个副本** —— 副本自删除走 `MOVEFILE_DELAY_UNTIL_REBOOT`，重启后才消失。
12. **UI 布局在 100% DPI 下验证** —— `app.manifest` 已声明 `PerMonitorV2`，但没有在 150%/200% 缩放下实测。
13. **向导的 `ui.logo` / `ui.backgroundImage` 未接线** —— 字段已预留，界面只用了 `accentColor` 与 `theme`。
14. **stub 体积 4.1 MB** —— AntdUI（2.6 MB）+ Core + UI + Newtonsoft 全部嵌入。换来的是一分发的单文件。
15. **制作端界面重做后那个渲染瑕疵消失了** —— 它是第一版标签页布局带来的，一屏三步的布局里不复现。
16. **制作端没有"打开/保存工程"按钮** —— 一屏三步是为了让**第一次做包的人**能用；批量/脚本场景请用 `installer-cli` + `.wmpkg.json`。`BuilderPresenter.Load/Save/ImportFromPackage` 都已实现，只是没在主界面上给入口。
17. **COM 注册无法逐条回滚注册表** —— DLL 自己写的内容记不下来，只能整体 `DllUnregisterServer`（见 §10.3）。
